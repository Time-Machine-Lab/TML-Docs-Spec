### 1.2 项目结构与目录规范 (Project Structure)
---
required: true
description: 用树形结构（tree 格式）描述项目的源码目录组织。明确每个一级目录的职责定位，并严格约束每个目录下**允许存放的文件类型**和**跨层调用的边界**。
format_instruction: 必须使用标准 `tree` 格式输出目录结构。每个目录后必须紧跟一行 `/**/` 注释说明其职责和约束。
example: |
  ```
  project-root/
  ├── cmd/                /**/ 应用程序入口点，一个微服务对应一个子目录，不放业务逻辑。
  │   ├── api-gateway/    /**/ 网关服务入口，仅负责请求路由和中间件串联。
  │   └── user-service/   /**/ 用户服务入口，仅负责依赖注入和启动。
  │
  ├── internal/           /**/ 私有应用程序代码，外部仓库禁止 import。结构由业务边界驱动。
  │   ├── domain/         /**/ 领域层：纯业务概念，无任何框架依赖。禁止引入 ORM 或 HTTP 框架。
  │   │   ├── user/       /**/ 用户领域：聚合根、实体、值对象、领域事件。
  │   │   └── order/      /**/ 订单领域：聚合根、实体、值对象。
  │   │
  │   ├── application/    /**/ 应用层：编排领域服务，处理用例。禁止直接操作数据库。
  │   │   └── user/       /**/ 用户用例：NewCreateUserUseCase, NewGetUserUseCase。
  │   │
  │   ├── infrastructure/ /**/ 基础设施层：实现领域接口的外部依赖（数据库、消息队列、第三方 SDK）。
  │   │   ├── persistence/ /**/ 数据库持久化实现，如 GORM Repository。
  │   │   └── messaging/   /**/ 消息队列发布/订阅实现。
  │   │
  │   └── interface/      /**/ 接口层：处理输入/输出协议适配，如 HTTP Handler、gRPC Server。
  │       ├── http/       /**/ HTTP 控制器：解析请求参数，调用应用层，组装响应。
  │       └── rpc/        /**/ RPC 控制器：处理来自其他服务的 gRPC 请求。
  │
  ├── pkg/                /**/ 内部共享库，仅限 project-root 内部使用。可被 cmd/ 和 internal/ import。
  │   └── logger/         /**/ 统一日志封装，提供结构化日志能力。
  │
  ├── third_party/        /**/ 外部依赖的副本或生成的代码，如 Protobuf 生成的 Go 文件。
  │
  └── scripts/            /**/ 构建、部署、代码生成的辅助脚本，禁止放业务逻辑。
  ```
