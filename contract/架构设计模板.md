  - "架构即取舍 (Architecture is Trade-off): 不要堆砌技术名词，重点解释为什么这么设计，不这么设计的代价是什么。"
  - "克制表达: 不要为了画图而画图。如果是单体应用，极简物理和过程视图；如果是微服务，则重点突出过程(时序)和物理(部署)视图。"
  - "架构文档分层原则: 架构设计负责定义'城市规划'，定义模块边界、职责划分、交互关系；领域/模块设计负责定义'每栋楼怎么建'，细化对象结构、状态机、约束；数据库/API/代码设计再往下才是'每个房间怎么布置'。"
out_of_scope:
  - 绝对不要在此讨论“具体的 API 请求参数”或“某一个特定按钮的业务逻辑”（属于需求/API文档）。
  - 绝对不要在此讨论“代码缩进、目录组织或 Git 分支流”（属于开发规范文档）。
  - 绝对不要在此列出具体的“对象属性列表”、“数据库表字段”或“枚举值集合”（属于领域模块设计文档）。

## 2. 逻辑视图：系统结构与模块边界 (Logical View)
---
required: true
description: 解决“系统是由什么组成的”。展示模块拆分和模块间的依赖关系。**重点是划分子系统/模块的边界（Boundaries）和明确每个模块的核心职责（Responsibilities），以及模块间如何交互。禁止在此描述任何对象的具体属性、字段或枚举值。**
format_instruction: 如果是微服务，列出核心服务划分及服务间依赖；如果是单体，列出核心模块及模块间依赖。可以使用图解进行描述，但图解中应只体现模块名称和交互箭头，不应出现字段名。
out_of_scope:
  - 禁止在此列出任何对象的属性（如：任务对象有 id、name、status 字段）。
  - 禁止在此定义数据库表结构、字段类型或索引设计。
  - 禁止在此列举枚举值或状态机的具体状态集合。
example: |
  **示例：电商系统逻辑视图（仅展示模块边界）**
  - **商品模块**：负责商品信息的展示和管理。**不关心**商品如何被购买、如何被推荐，只关心“我能提供什么标准的商品信息”。
  - **交易模块**：负责订单的创建、支付和履约。**不关心**商品信息如何存储，只关心“我能协调哪些服务完成一笔交易”。
  - **交互关系**：交易模块依赖商品模块提供的标准接口获取商品信息；用户模块依赖交易模块的数据进行行为分析。
  （注：此处不描述商品对象有哪些字段，也不描述交易流水表有几列）
